Get started

Quick start #

evrd keeps your IRC connection alive while you're away, buffers what you miss, and lets clients (native or web) attach and detach whenever you like. The quickest way to run it is with the published container images: ghcr.io/4evrd/evrd (the daemon and evrctl) and ghcr.io/4evrd/evrd-web (the web app on nginx).

  1. Make a secret key

    It encrypts the network passwords evrd saves (SASL and server passwords) and secrets set in Admin → Settings. Keep a copy somewhere safe; without it they can't be read back.

    shell
    echo "EVRD_SECRET_KEY=$(docker run --rm --entrypoint evrctl ghcr.io/4evrd/evrd genkey)" > .env
  2. Write a config file

    A single node needs no external database: SQLite holds accounts and an embedded Pebble store holds history.

    evrd.conf
    listen     ircs://:6697
api        :8098
db         sqlite:/var/lib/evrd/evrd.db
history    pebble:/var/lib/evrd/history
public_url https://bnc.example.org
irc_host   bnc.example.org
cookie_secure no   # until TLS is in front — then remove this line
  3. Start evrd and the web app

    The web image proxies /api and /auth to evrd-api:8098, so name the daemon's service that (or point the web container at it with EVRD_API=host:port).

    docker-compose.yml
    services:
  evrd-api:
    image: ghcr.io/4evrd/evrd:latest
    command: ["-config", "/etc/evrd/evrd.conf"]
    environment:
      EVRD_SECRET_KEY: ${EVRD_SECRET_KEY}   # from .env
    volumes:
      - ./evrd.conf:/etc/evrd/evrd.conf:ro
      - evrd-data:/var/lib/evrd
    ports:
      - "6697:6697"   # IRC — clients attach here
    restart: unless-stopped
  evrd-web:
    image: ghcr.io/4evrd/evrd-web:latest
    ports:
      - "8080:80"     # web app; put TLS in front of it
    restart: unless-stopped
volumes:
  evrd-data:
  4. Create the first admin
    shell
    docker compose exec evrd-api evrctl -config /etc/evrd/evrd.conf \
  user add -admin james 'a-long-password'
  5. Sign in and add a network

    Open the web app (port 8080, or your public_url once a TLS proxy is in front), sign in, and add a network such as irc.libera.chat on +6697. evrd dials it, registers, autojoins your channels and starts buffering. Then attach a native client.

Passwords need at least 10 characters. A password an admin sets in the web app (Admin → Users) is temporary: the user picks their own at next sign-in. Passwords set with evrctl aren't. Once TLS is in front of the web app, remove cookie_secure no so the session cookie is HTTPS-only. For Postgres and metrics, the repository's deploy/docker setup has them ready.

Install on OpenBSD #

evrd runs natively on OpenBSD (amd64 and arm64), without Docker. One script installs it as a confined system daemon, with SQLite and the embedded Pebble history store, so there's no database server to run. One command, as root (ftp is OpenBSD's built-in downloader, so no curl is needed):

shell
ftp -o - https://raw.githubusercontent.com/4evrd/evrd/main/deploy/openbsd/install.sh | sh

The questions come up at your terminal even though the script arrives through a pipe. Not root? Use | doas sh. It downloads the latest release for your machine, checks it against the release's SHA256 file, and asks:

Host name for the web appthe machine's namee.g. bnc.example.org

HTTPS port, Let's Encrypt email443, none
IRC host name and portsthe web host, 6697 (TLS), no plain port
Single sign-onnonean OpenID Connect issuer (e.g. Logto's https://id.example.org/oidc), client ID, secret (not echoed), button label and admin role. It shows the redirect URI to register: <web app>/auth/callback
Admin username and passwordnonethe first admin account

Then it starts evrd and prints the address. Open the ports in pf (/usr/local/share/examples/evrd/pf.conf has the rules). For Let's Encrypt, the names must already resolve to the machine, with ports 80 and 443 reachable. Every question has an option (-d host, -c certificate, -w evrd|relayd, -o SSO issuer, -a admin, …), passed as | sh -s -- -y -d bnc.example.org …. -y takes the defaults, for provisioning without a terminal. Run the same command again to upgrade: it keeps the config and the key. evrd restarts only if its program changed (a release that only touches the web app goes live without one), and even then nobody leaves IRC: the connection holder, evrd-links, keeps everyone's connections open while evrd restarts. Certificate renewals reload evrd (rcctl reload evrd) instead of restarting it.

How evrd is confined

rc.d starts evrd as root. It binds its ports and reads /etc/evrd/evrd.conf, the secret key and any certificate files, then:

  1. chroots to /var/evrd, so the rest of the filesystem is gone;
  2. becomes _evrd. The chroot and everything in it but data/ belong to root, so evrd can't change its own web app or name resolution;
  3. unveils only its data, the web app and resolv.conf / hosts (read-only);
  4. pledges stdio rpath wpath cpath fattr flock inet dns unix sendfd: it can't execute anything or open other kinds of sockets (unix sendfd hands connections to the holder).

evrd-links is confined the same way but tighter: chrooted to /var/evrd as _evrd, it pledges only stdio inet unix recvfd and can't open any files.

PathWhat
/etc/evrd/evrd.confthe config (root:_evrd, 0640)
/etc/evrd/secret.keyencrypts saved network passwords and certificate keys. Back it up, apart from the data
/var/evrd/data/the database and history (_evrd only)
/var/evrd/web/the web app, served by evrd (web_root)
/etc/rc.d/evrdrcctl start|stop|restart|reload evrd; logs go to /var/log/daemon
/etc/rc.d/evrd_linksthe connection holder, started before evrd. Its socket is /var/evrd/run/links.sock. Restarting it drops the IRC connections, so the installer only does that when a release changed it

The same confinement works anywhere evrd starts as root, with chroot and user in evrd.conf (unveil and pledge are OpenBSD's).

To upgrade, run the same command again. It keeps evrd.conf and the key (it asks; -y keeps them) and replaces the programs and the web app. evrd restarts only when its program actually changed, and the connection holder keeps everyone on IRC while it does; the holder itself is restarted only when the new evrd can't talk to the old one (or at the next reboot). Database changes are applied at startup. To back up, stop evrd, copy /var/evrd/data/, start it again, and keep /etc/evrd/secret.key somewhere else. For oidentd, see oidentd.

Build from source #

evrd is pure Go (no cgo), so it cross-compiles anywhere Go 1.26 runs. The web client is a Svelte 5 + Vite app built with pnpm.

shell
git clone https://github.com/4evrd/evrd.git && cd evrd
make build       # bin/evrd and bin/evrctl
make web         # web/build
./bin/evrd -version
./bin/evrd -config evrd.conf

Development stack

make up runs the whole stack with hot reload: an upstream ergo IRC server, two evrd nodes behind nginx, Postgres, ScyllaDB, VictoriaMetrics and the web client on http://localhost:5173. make e2e runs the Playwright suite against it.

Use evrd

Web client #

The web app shows your networks, channels and private messages with unread counts, mentions, members and topics, and stays in sync with every attached IRC client. Anything you send there shows up in your other clients too, because all sessions share one upstream connection.

The chat input understands /join, /part, /msg, /query, /me, /notice, /nick, /topic, /mode, /kick, /close, /quote and /help, and runs *status commands with /status help (all but jump, playback and detach, which are for IRC clients).

Use evrd

Languages and translations #

The web app comes in English, Italian, Spanish, Turkish, German, Indonesian and Japanese. It follows the browser's language until you pick one under Account → Profile → Language; dates, times and numbers follow it too. What IRC networks and evrd's server send (connection logs, errors) stays as it is.

Translations can be uploaded. Admins publish them for everyone under Admin → Settings → Languages; anyone can upload one for themselves under Account. An upload either changes a language on offer (only the texts it has; the rest stay) or adds a new one. When a text is missing, evrd uses your own file, then the admin's, then the built-in translation, then English.

FormatFilesNotes
gettext PO.po, .potFor Poedit: the .po template opens as is; the language and plural forms come from its header. Entries marked fuzzy are skipped.
CSV.csvColumns key, english, translation, for spreadsheets.
XLIFF.xlf1.2 and 2.0, for translation tools.
JSON, YAML.json, .yamlevrd's own format, flat or nested keys.

Download a template (every English text, nothing translated) or any language as it is now, in each format, from the same pages. Before saving, the upload shows what's in the file; a {placeholder} that differs from English blocks it. Uploaded text is always shown as text, never as HTML.

evrd's own words

What evrd itself says is translated too: *status's replies and its help, the welcome lines and PART reasons IRC clients see, errors over IRC and on the website, a network's connection log (why a connection failed or dropped, and what to do about it), the activity feed and notifications, the admin overview's "needs attention", and the modules' and Admin → Settings' labels and help. They're the keys starting with irc. in the same language files; a file can have only those, only the web app's, or both.

Over IRC, evrd answers in the language picked under Account → Profile → Language (with the browser's language picked, IRC replies are in English). On the website these messages follow the language the app shows. The connection log and the activity feed keep what evrd said, not the sentence, so they read in each viewer's language: an admin helping a user sees the user's log in their own. What IRC servers and services say is shown as they sent it.

Command names, settings and their values (connect, set nick …, on, off) stay the same in every language. Lines before an IRC client has signed in, IRC protocol replies (numerics, FAIL, BOUNCER errors), the server log, and errors in evrd.conf or the network directory's file are in English. IRC clients get …, —, · and curly quotes as plain ASCII; letters in any script pass through as written.

Uploading a translation

Admins upload one for everyone under Admin → Settings → Languages: a new language (de) or changes to a built-in one (it). It's kept in the database, so every node of a cluster has it within 30 seconds. Every user can upload one for themselves under Account → Profile → Your own translation; it shows up in their Language menu. For each text the app uses the first of: your own translation (when its language is the one you picked), the admin's, the built-in language, English. So a file doesn't have to be complete: to fix one Italian string for yourself, upload a file for it with only that string.

The file is converted to evrd's JSON in your browser before it's uploaded. Before saving, the upload shows what's in it. These stop it:

  • a bad language code (2 or 3 lowercase letters, with a region like pt-BR) or name, or a bad key;
  • a text over 2,000 characters, or a file over 512 KiB;
  • placeholders such as {count} that differ from English (they may move within the sentence);
  • a plural without other. Plurals have a form per CLDR category (zero, one, two, few, many, other); in PO they follow the file's Plural-Forms.

Keys English doesn't have are a warning and ignored. The upload also says how many texts are still untranslated, and how many fuzzy PO entries were skipped. When the file doesn't name its language (CSV, a flat JSON file), the upload asks for the code and the name in the language itself.

Native IRC clients #

Point HexChat, irssi, WeeChat or any other IRC client at the bouncer and authenticate with a server password:

Server passwordAttaches to
user:passwordyour first network (the oldest one you added)
user/network:passworda specific network

The password is either your account password or an IRC client password made on the web app's IRC clients page, revocable one client at a time. Accounts that sign in with SSO use a client password, sign in by link, or their SSO password where the admin turned that on. Clients that do SASL can sign in with SASL PLAIN instead (user name user or user/network). All the ways are under Signing in from IRC clients.

irssi
/connect -tls bnc.example.org 6697 james/libera:a-long-password

What you get on connect

  • The welcome burst, your channels with names and topic, backlog replay, then live traffic.
  • /join and /part update the network's saved channel list, and /nick changes your nick upstream.
  • Your own notices and /me actions are saved and shown on your other clients.
  • IRCv3 capabilities for clients that ask for them; a client that asks for none gets plain IRC.

Channel events in backlog

Joins, parts, quits, kicks, nick changes, topics and modes are saved with the messages, and the web chat shows them. Backlog replays them only to a client that asks for draft/event-playback, as the real lines in a history batch (see IRCv3). Other clients get just the chat, so replay never confuses their nick lists. Either way the backlog's line count counts only what's replayed. (Before v0.32.0 events were replayed from *buffextras; that's gone.)

Port 6667 is plaintext. Use 6697 with TLS anywhere outside a private network, and set tls_cert / tls_key for a real certificate.

Signing in from IRC clients #

An IRC client signs in with a server password of user:password or user/network:password. The password can be:

  • the account password, for accounts that have one;
  • an IRC client password, made for one device on the web app's IRC clients page and revocable on its own;
  • the SSO password, for accounts that sign in with SSO, where the admin turned that on (sso_irc_password; the IRC clients page says so).

Clients that do SASL can sign in with SASL PLAIN instead, with the user name user or user/network. Any account, SSO or not, can also sign in by link.

Signing in by link

Connect without a password: server password mira, mira/libera, or none at all. evrd registers the client on no network and *status sends a link:

*status
<*status> Sign in on the website to connect: https://bnc.example.org/irc/approve/… (the link works once, for 5 minutes).

Open it, sign in the way you do on the website (your identity provider and its MFA included), check the client it shows (nick, network, address, time) and Allow it: the client is put on its network. Turn away closes it.

Allow only a client you just connected yourself. Someone who sends you a link would get into your account. The page says so, and points out when the client connects from another address than yours.

Allowing can remember the device for irc_remember_days (30 by default), either with a new IRC client password, shown once on the page, to put in the client's server password; or with the password the client sent, if it was a long one (24 characters or more) evrd didn't know. Put a long random string in the client's server password, connect, allow it with "the password the client sent", and from then on it signs in by itself. Remembered devices are listed on the IRC clients page with their end date and revoked there like any client password.

A link is good for one connection: it goes when the client disconnects, and a client waits five minutes at most. At most three links are open per address and five per account. It's on by default when public_url is set; irc_link_signin no turns it off.

A second factor

With an authenticator app set up on Account → Security, IRC sign-ins with your password can also ask for a code from it: when you turn on Require a second factor for IRC, or always if the admin requires it. Either send the code after the password:

server password
mira/libera:<password>:123456        # or a recovery code: …:<password>:abcd-efgh

or sign in as usual: evrd registers the client on no network and *status asks for the code (or, with sign in by link on, offers to allow the sign-in on the website instead, which works without an authenticator app too). Nothing else works until it's in:

irssi · *status
<*status> A second factor is needed before you're on libera: /msg *status otp <code>, …
/msg *status otp 123456
<*status> Second factor accepted.

You have two minutes and five tries; then the connection closes and you sign in again. Ten recovery codes, shown once when the app is set up, work instead of a code, once each. A client waiting for its code isn't kept through an evrd restart; a client the connection holder kept through a restart isn't asked again.

IRCv3 #

A client that asks for no capabilities gets what IRC clients always got from evrd. A client that asks gets IRCv3: evrd's own capabilities, offered on every network, and the network's, passed through while the network has them. evrd asks the network for each one it passes through when the network offers it.

A client picks its network with PASS, SASL or BOUNCER BIND. Clients send CAP LS first, usually with PASS, NICK and USER right behind, so evrd's answer waits for those (at most a second and a half) and then offers the network's capabilities too. When the network isn't known by then (SASL comes after CAP LS), they follow as CAP NEW once the client is attached. CAP NEW and CAP DEL also come when the link gains or loses one or the client jumps networks. A CAP REQ is ACKed or NAKed whole: one that asks for a capability that isn't offered (yet) is NAKed. Lines a capability brings reach the clients that asked for it; the others get them translated, or not at all.

Scrollback (chathistory)

Clients page through history with CHATHISTORY LATEST|BEFORE|AFTER|AROUND|BETWEEN <buffer> … (by msgid= or timestamp=) and find the buffers with news since they were last here with CHATHISTORY TARGETS. Replies come in a chathistory (or draft/chathistory-targets) batch, and mistakes as FAIL CHATHISTORY … standard replies. A client sees the network it's attached to and nothing else. Without draft/event-playback, only messages, notices and actions come back, and events don't count against the limit.

A timestamp= stands for its whole millisecond (the precision of @time); msgid= is exact, so evrd lists it first. Clients that negotiate chathistory get CHATHISTORY=1000 MSGREFTYPES=msgid,timestamp in ISUPPORT: at most 1,000 lines per request (more is capped, not refused). Replayed and fetched lines carry the nick only (evrd doesn't keep user@host), so their prefix is nick!nick@<network>. AWAY, ACCOUNT, CHGHOST and SETNAME aren't kept in history.

Networks from the client

SASL. Instead of PASS, a client can sign in with SASL PLAIN: the user name (or user/network) and the account password or an IRC client password. Accounts that sign in with SSO need a client password, as with PASS.

soju.im/bouncer-networks. Goguma and gamja list, add, change and remove your networks from the client (BOUNCER LISTNETWORKS, ADDNETWORK, CHANGENETWORK, DELNETWORK, with soju's attributes name, host, port, tls, nickname, username, realname, pass, and read-only state and error), within your network limit. A client that asks for the capability and names no network gets a bouncer connection on no network; it opens one connection per network with BOUNCER BIND <id> (ISUPPORT BOUNCER_NETID). Each connection counts against your client limit. With soju.im/bouncer-networks-notify it hears when networks come, change (their state too) and go, within a few seconds.

Read markers

MARKREAD (draft/read-marker) reads and moves how far a buffer is read. They're the same markers the web app uses, so reading on one client or in the web app shows as read on the others within a few seconds. A marker only moves forward. A client gets a channel's marker after its JOIN.

Typing, tags and msgids

Client-only tags (+typing, +draft/reply, +draft/react…) pass both ways for clients with message-tags, when the network has message-tags: TAGMSG lines (typing notifications, reactions) and the + tags on messages and notices. Your typing also shows on your other attached clients; echo-message sends a client's own back. TAGMSGs are never saved. Of the network's own tags only @account (with account-tag) and @bot pass; a client can't send anything but + tags.

Clients know lines by evrd's msgids. evrd remembers the network's msgid for the last few thousand lines of each network, so replies, reactions and redactions (REDACT) name the right line both ways. evrd doesn't learn the network's msgid for what you send, so redacting your own line works only where the network accepts it otherwise. A redaction doesn't remove the line from evrd's history.

Also passed through: the network's ISUPPORT (005: PREFIX, CHANTYPES, MONITOR, BOT…) with evrd's own tokens; MONITOR itself (one list per network, shared by your clients); and bot mode (BOT=, +B and the @bot tag, for clients with message-tags). Not supported: draft/metadata-2.

Labels, multiline, STS

labeled-response is offered only while the network has it. What evrd answers itself (*status, CHATHISTORY, BOUNCER, MARKREAD, echoes) evrd labels; other commands go to the network with the label, and the network's labeled reply goes back to the client that sent it. Your other clients get the same lines without the label.

draft/multiline is offered while the network has it, with the network's max-bytes and max-lines. A multiline message goes to the network as one batch and is saved a line at a time; each saved line has its own msgid.

sts tells clients to use TLS only. It's offered only with a TLS listener and a certificate clients trust: see STS. no-implicit-names sends only the NAMES replies the client asked for. draft/pre-away: an AWAY sent while registering is set once attached (AWAY * is left to auto-away).

Clients

Goguma, gamja, Halloy and Senpai use chathistory, read markers and bouncer networks, as they do with soju. Recent WeeChat takes the batched backlog with server-time. irssi, HexChat and mIRC take the backlog as plain lines.

ZNC's names work too (ListNetworks, JumpNetwork, AddNetwork, the …TrustedServerFingerprint commands…), and so does ZNC's raw command: /znc ListNetworks (or /quote znc …) is the same as /msg *status ListNetworks. Playback buffers #

Each channel and private message has a buffer, per network. When an IRC client attaches it gets each buffer's last lines: how many is set under Account → Bouncer (playback lines), with setbuffer for one network or one buffer (0 to 500).

A buffer that auto-clears plays back only what came since an IRC client was last on that network, and nothing while another client is on it, as with ZNC's AutoClearChanBuffer and AutoClearQueryBuffer. Set it under Account → Bouncer for channels and for private messages, or with autoclear for one buffer. clearbuffer starts a buffer over, and playback <buffer> [lines] replays its last lines from history whether it was cleared or not.

irssi · *status
/msg *status buffers                  # lines, auto-clear, what's waiting
/msg *status setbuffer #evrd 200
/msg *status autoclear #evrd off
/msg *status playback #evrd 50

The network's page in the web app has the same settings under Playback: lines per buffer for the network, each buffer's lines and what it plays back, what's waiting, and clearing. The lines stay in history either way: the web chat, playback and CHATHISTORY still have them. A client with draft/chathistory gets no playback; it asks for what it wants (see scrollback).

Playback for clients without server-time carries timestamps in the text ([12:34:56] hello). Change the format (strftime), time zone and whether they're prepended or appended under Account → Bouncer.

Network settings #

Each network has its own page in the web app (/networks/<id>) with everything ZNC offers without modules.

  • Servers: several, each with host, port, TLS and an optional server password. evrd connects to the first and moves on to the next each time the link drops.
  • Identity: nick, alternate nick, ident, real name, quit message and bind host. Empty fields use the account defaults.
  • Authentication: how evrd logs in to services: SASL PLAIN, IDENTIFY to NickServ, a command of your own, or none, with presets for common networks. See Logging in to services.
  • Certificates: verify with system CAs (TrustPKI), trust everything (TrustAllCerts), or trusted SHA-256 fingerprints. When a certificate is refused, its fingerprint is shown with a button to trust it.
  • Channels: key, detached (joined and logged but hidden from IRC clients until they /join), join-on-connect.
  • Advanced: encoding for non-UTF-8 networks (^charset: only decode invalid UTF-8; charset: decode and send in it), flood protection (lines per second and burst), join delay.
  • Modules: optional behaviours per network; see Modules.

Network directory

Add network starts with a searchable list of public networks — Libera.Chat, OFTC, EFnet, IRCnet, Undernet, DALnet, QuakeNet, Rizon and more. Picking one fills in its servers (TLS where the network's certificate checks out) and suggested channels; only your nickname is left. Enter details manually is there for anything else, and from an IRC client /msg *status directory [search] lists it and addnetwork <id> adds one.

evrd fetches the list from https://evrd.sh/api/networks/v1.json (schema) at startup and twice a day, and keeps the last good copy in its database. network_directory points it elsewhere — a URL or a file of your own — or off. New networks and changed servers are welcome as pull requests to api/networks/; each entry needs an id, a name and its servers, as the schema describes. List a TLS server only when its certificate is publicly trusted and matches the host name, since evrd verifies it. To know roughly how many evrd installs there are, evrd.sh counts these fetches: one per install per day, keeping only the day, the version and a salted hash of the address that changes daily (never the address), for 90 days. With network_directory off or your own source, you aren't counted.

Per-user settings

Under Account → Bouncer: default ident, quit message and bind host; how many lines to play back, and whether channels and private messages only replay what arrived since an IRC client was last on that network; timestamps for clients without server-time (strftime format, time zone); fixed CTCP replies (an empty reply blocks the request; with no client attached evrd answers VERSION, PING and TIME itself); and the addresses allowed to sign in, on the web and over IRC. Under Account → Profile, Mark me away when no client is attached sets you away on every network while no IRC client or web app is attached.

Logging in to services #

Most networks keep accounts in services: NickServ on Atheme and Anope networks (Libera.Chat, Rizon…), on DALnet a NickServ at NickServ@services.dal.net, X on Undernet, Q on QuakeNet. evrd logs in to yours every time it connects. Set it up on the network's page under Authentication, or with *status set.

MethodWhat evrd does
Automatic (auto, the default)SASL PLAIN while connecting when the network offers it. Without SASL, or when SASL is refused, it sends the password as PASS and, once connected, IDENTIFYs to NickServ.
SASL only (sasl)SASL PLAIN, nothing else. If the network has no SASL or refuses the login, the connection log says so and evrd stays logged out.
IDENTIFY to NickServ (nickserv)No SASL: once connected, PRIVMSG NickServ :IDENTIFY … to the services nick.
A command of my own (command)Once connected, sends your line: raw IRC or /msg target text, with %account%, %password% and %nick% filled in. For services that aren't NickServ, like Undernet's X.
Don't log in (none)Nothing, or the q module logs in to QuakeNet's Q.

SASL EXTERNAL (logging in with a client certificate) isn't offered: evrd doesn't present client certificates to networks. The account name is your services account (empty: your ident for SASL, your nick for NickServ). The password is stored encrypted and never sent back to the browser.

Options

  • Services nick: where IDENTIFY goes: NickServ (empty), or NickServ@services.dal.net on DALnet. /NS (or /NICKSERV) sends the server's own command instead, for networks that only accept that.
  • IDENTIFY sends: account sends IDENTIFY account password (Atheme, Anope 2); password sends just IDENTIFY password, for older services that identify you to the nick you're on; empty sends the account only when it isn't the nick in use.
  • Identify: as soon as evrd is connected, or when NickServ asks ("This nickname is registered…"). When it never asks, evrd identifies after 10 seconds anyway.
  • When the nick is taken: evrd connects on the alternate nick, logs in, then asks services to GHOST, REGAIN or RECOVER the nick (with the password) and switches to it.
  • Join channels after identifying: holds the channel joins until services confirm the login, so channels only logged-in users may join (+r, +R) let evrd in. If services don't answer within Wait for services seconds (default 15), evrd joins anyway.

Modules #

Modules are optional behaviours you switch on per network, like ZNC's network modules. Switch them on and set them up on the network's page (Networks → the network → Modules), or from an IRC client with *status. Changes apply when you save, without reconnecting; perform's commands run at the next sign-in. What modules do shows in the network's connection log.

irssi · *status
/msg *status modules                       # which are on, and what each does
/msg *status loadmod keepnick              # switch one on for this network
/msg *status unloadmod keepnick            # and off
/msg *status modset kickrejoin delay 5     # change a setting
/msg *status modset perform commands /mode %nick% +i | /msg NickServ ghost me

HTTPS and certificates #

evrd's own TLS ports (the ircs:// IRC listeners, and the web app when evrd serves HTTPS itself) share one certificate source. Set it with tls, or switch it while evrd runs under Admin → Settings → HTTPS & TLS:

tlsCertificate
acmeLet's Encrypt: evrd gets one for each name in acme_hosts (default: public_url's host and irc_host) on first use, and renews it 30 days before it expires. Picking it accepts the CA's subscriber agreement.
selfsignedMade once and kept. Browsers and IRC clients ask you to accept it. The default without tls_cert.
filestls_cert and tls_key (PEM, with the chain) from certbot, acme-client or your own CA, re-read when the file changes and on SIGHUP (rcctl reload evrd), without a restart.

Certificates evrd gets or makes, and its ACME account, are kept in the database, encrypted with secret_key. Every node of a cluster serves the same ones, and nothing is written to disk.

Who serves HTTPS

evrd itself: set https_listen and http_listen, and web_root to the built web app. No proxy or web server is needed. Port 80 redirects to HTTPS and answers Let's Encrypt's http-01 challenge, and 443 answers tls-alpn-01.

evrd.conf
public_url   https://bnc.example.org
irc_host     bnc.example.org
https_listen :443
http_listen  :80                     # redirects, and Let's Encrypt's challenges
web_root     /var/lib/evrd/web       # the release archive's web/
tls          acme
acme_email   ops@example.org         # optional: expiry notices

A proxy in front (nginx, Caddy, Traefik, relayd, a cloud load balancer): leave https_listen unset. The proxy terminates TLS and forwards to api, including the WebSocket, and evrd's certificate is then only for the IRC ports. This is how the Docker images run.

The settings page says which of the two is in use, and shows each certificate's issuer, names and expiry, or why getting one failed. Saving a choice that can't work (Let's Encrypt for localhost, say) is refused.

STS: TLS only for IRC clients

With an ircs:// listener and a certificate clients trust for irc_host (Let's Encrypt, or files from a public CA, never selfsigned), evrd offers IRC clients the IRCv3 sts capability: a client on a plain port is told the TLS port, and one on TLS how long to keep to it (irc_sts, 24h by default, or off). Clients that support it (Goguma, gamja, Halloy, Senpai, WeeChat…) then connect with TLS only, and refuse a plain connection until that time runs out.

That's a lock-in: once a client has seen it, taking TLS away (removing the ircs:// listener, or a certificate that expires or no longer matches) locks it out until the duration passes. Keep the duration modest, and set irc_sts off, and wait that long, before removing TLS. evrd checks the certificate every few minutes and stops offering sts as soon as it isn't one clients would trust.

Proxies and the web app

trusted_proxies (or EVRD_TRUSTED_PROXIES; file or environment only) lists the proxies whose X-Forwarded-For is believed: addresses or CIDR ranges, the local host by default. From anywhere else the connection's own address counts, and it's what each user's allowed addresses are checked against. Set it to the proxy's network when the proxy isn't on the same machine (Docker: 172.16.0.0/12).

The web app has no inline scripts, so a proxy that sets a strict Content-Security-Policy on every site (script-src 'self', no 'unsafe-inline') doesn't break it; it only needs connect-src 'self' for its API and WebSocket.

# logto_m2m_resource     https://default.logto.app/api   # only if the default is wrong

However it's checked:

  • The order is: IRC client password, then the evrd password, then the SSO password. A local account (not linked to SSO) is never sent to the provider.
  • A right password is remembered for 10 minutes (only a keyed hash of it, in memory), so a reconnecting client doesn't ask the provider each time. A wrong one is never remembered.
  • Failed sign-ins count toward the same lockout as the web sign-in: 10 within 15 minutes.
  • If the provider can't be reached, the sign-in is refused, never let through ("can't check your SSO password right now"); client passwords keep working, and it doesn't count toward the lockout.
  • The activity feed says a client signed in with the SSO password, and how it was checked.

Keep the secrets (sso_password_client_secret, ldap_bind_password, logto_m2m_client_secret; Logto's app can read and change every user) in environment variables or Settings, where they're stored encrypted, not in a world-readable file.

Provisioning API

For tools that bring users in from elsewhere, such as moving ZNC users over, evrd can create an account and its networks before the owner ever signs in. It's off until provision_token is set (or EVRD_PROVISION_TOKEN), and every call sends that token:

shell
curl -X PUT http://127.0.0.1:8098/api/provision/users/alice \
  -H "Authorization: Bearer $EVRD_PROVISION_TOKEN" \
  -d '{"email": "alice@example.org", "connect": true,
       "networks": [{"name": "libera", "host": "irc.libera.chat", "port": 6697,
                     "tls": true, "nick": "alice", "channels": ["#evrd"]}]}'

Networks take the same fields as the web app's network editor. Each one comes back as created, exists (so a call can be repeated) or failed. connect connects every listed network, so a migration can create everything, take the old bouncer off IRC, then call again to connect. A new account has no password and is claimable: the first SSO sign-in with the same username and email links to it. Keep the token secret and the API on a local address.

Limits, suspension and passwords

Server defaults, which admins override per user (0 = unlimited): max_networks 0, max_clients 0 (attached IRC clients at once) and backlog_lines 2000 (kept per channel, pruned every 10 minutes).

Suspending a user signs them out everywhere, drops their IRC clients and disconnects their networks; lifting the suspension reconnects them. The last active admin can't be demoted, suspended or deleted.

Passwords need at least 10 characters. A password an admin sets, or the one-time password Reset generates on the Users page, is temporary: the user picks their own at next sign-in. Users can delete their own account under Account.

Server settings #

Admins can change the general, limits, connection (connect_rate, bindhost), HTTPS & TLS, sign-in, single sign-on and metrics settings from Admin → Settings. Each value comes from, in order (later wins):

  1. built-in defaults
  2. evrd.conf
  3. the database: values set on the Settings page, shared by every node
  4. the environment on that node (EVRD_OIDC_CLIENT_SECRET, EVRD_METRICS_URL, OTEL_EXPORTER_OTLP_METRICS_ENDPOINT)

Most settings apply live on every node within a few seconds. public_url, the SSO provider, metrics export and the certificate file paths are marked Restart needed. With the connection holder running, that restart doesn't take anyone off IRC. Startup and per-node settings (listen, api, https_listen, http_listen, web_root, chroot, user, db, history, cluster settings, upstream_bind / upstream_prefix6, secret keys, settings_write_conf) stay in the file or environment.

settings_write_conf yes writes values set in the UI back into each node's own config file; the file's directory must be writable by evrd (not a read-only single-file mount). Use it on a single node; in cluster mode, leave it off and let the database be the one place these settings live.

Saved passwords #

Network passwords (the SASL password and server passwords), a network's services login command, its module settings, the values set in Admin → Settings (such as the SSO client secret) and the keys of the certificates evrd keeps are encrypted in the database with AES-256-GCM under a key that lives outside it. Without a key evrd still runs and warns that these are stored in plaintext. Account and client passwords are bcrypt hashes either way.

evrd.conf
# make one with: evrctl genkey
secret_key      <32 bytes, base64>   # or EVRD_SECRET_KEY, or secret_key_file /path
secret_key_old  <previous key>       # optional: still decrypts while rotating

Rotating the key

Set the new secret_key, move the old one to secret_key_old, restart, then remove the old key. At startup evrd encrypts anything saved before a key was set and re-encrypts anything under an old key: network passwords, module settings and settings alike. Every node needs the same key; keep it out of database backups.

Connection holder #

evrd-links keeps users' IRC connections open while evrd restarts. Run it first, as root, with the same chroot and user, and point evrd at its socket:

shell · evrd.conf
evrd-links -socket /var/evrd/run/links.sock -chroot /var/evrd -user _evrd

links_socket /var/evrd/run/links.sock   # evrd.conf

evrd opens each connection to an IRC network itself and hands the socket to the holder, which does TLS and passes lines both ways. When evrd stops (to upgrade, or for a setting that needs a restart) the holder keeps the connections: it answers the servers' pings and buffers what arrives (4 MB per network; -buffer changes it). The next evrd takes each one back without registering or joining again, and replays the buffered lines into history. Switching a network off, or deleting it, still quits it.

The holder keeps evrd's IRC clients connected too (hold_clients yes, the default). evrd hands it the IRC listeners, with the certificate for TLS ones, and the holder accepts the clients, so a restart is invisible to them: no disconnect, no second welcome, no rejoining. While evrd is away the holder answers their pings and keeps what they send (64 KiB each); the next evrd picks each one up where the last left it, and what the networks said meanwhile reaches them with its real time. Clients that connect while evrd is down wait for it; one evrd isn't back for within 2 minutes is told to reconnect. hold_clients no turns this off. An older holder (protocol 1) holds no clients; evrd then listens itself, and restarting the holder brings it in (evrd-links -version says which).

Without the holder, evrd connects directly. Restarting the holder itself drops the connections, so it's built to change rarely; the OpenBSD installer restarts it only when its program changed. In Docker, run evrd in the holder's network namespace (network_mode: "service:links") so the connections outlive evrd's container. The holder is for a single node: in a cluster, users move between nodes instead, and links_socket is ignored. Diagrams are on the architecture page.

Running several nodes #

Run any number of nodes against the same Postgres and ScyllaDB, behind a plain round-robin load balancer for IRC (TCP passthrough) and the API (HTTP + WebSocket). Each user is owned by one node, which runs their network connections and serves their clients; any other node forwards that user's traffic to it.

If a node dies, its users move to the others in about 20 seconds (cluster_lease); on shutdown a node hands them over within one tick (5 s).

evrd.conf · every node
internal_listen      :8099   # internal HTTP — between nodes only
internal_irc_listen  :6699   # internal IRC — between nodes only
history              scylla://db1,db2/evrd
environment · per node
EVRD_NODE_ID=node-a
EVRD_INTERNAL_URL=http://evrd-a.internal:8099
EVRD_INTERNAL_IRC_ADDR=evrd-a.internal:6699
EVRD_CLUSTER_SECRET=<the same long random secret on every node>

See the architecture page for diagrams of each deployment shape, request routing and failover.

The repository ships a tested nginx config (deploy/lb.conf) and a Traefik equivalent (deploy/traefik/, Traefik ≥ 3.7 for TCP health checks). With internal_listen set, all four of cluster_secret, internal_url, internal_irc_listen and internal_irc_addr are required (as directives, or the environment variables above). A lone node without internal_listen still works and owns every user.

Connections to networks #

Large networks throttle and cap connections per source address, and every user on a node would otherwise share the node's address. evrd connects to IRC servers over IPv6 first, falling back to IPv4 (prefer_ipv6 yes; no tries IPv4 first, and with only IPv4 upstream_bind addresses IPv4 goes first either way). Connects to one server host are spaced to connect_rate per second per node, and reconnect backoff is jittered, so a takeover or a netsplit recovery reconnects users gradually.

evrd.conf
connect_rate     5                       # most connects/second to one server, per node
upstream_bind    192.0.2.10 192.0.2.11   # spread users over these (stable per user)
upstream_prefix6 2001:db8:42::/64        # each user's own IPv6 address (IPv6 servers)
bindhost         192.0.2.20 vhost.example.org

upstream_bind and upstream_prefix6 are per node (EVRD_UPSTREAM_BIND, EVRD_UPSTREAM_PREFIX6); either way a user always connects from the same address. A prefix needs Linux and a local route: ip -6 route add local 2001:db8:42::/64 dev lo.

Bind hosts

bindhost (repeatable) lists local addresses users may pick to connect from, like ZNC's BindHost, for their whole account or per network (setbindhost, setuserbindhost in *status). On Linux an IPv6 bind host may come from a routed prefix with only a local route for it, as with upstream_prefix6: evrd binds it with IPV6_FREEBIND, so nothing has to be added to an interface per address. Admins may use any address and can lock a user's choice (DenySetBindHost).

When a server refuses

A link that drops after working for a while reconnects at once. One cut off soon after connecting keeps backing off, up to five minutes. A server that refuses this address (a K-line, banned, not authorised to use this server) rests for half an hour, doubling to four hours while it keeps refusing, and one that says you reconnect too fast rests two minutes. Meanwhile evrd tries the network's other servers; only when every one is resting does it wait.

Ident

Some networks want an ident answer (EFnet servers refuse "No Ident response"). evrd can answer for its own connections, matching each query to the user's connection even behind NAT or Docker, or keep an oidentd file from users' bind hosts:

evrd.conf
identd_listen    :1113                   # evrd answers ident (map public port 113 here)
ident_file       /var/evrd/ident/.oidentd.conf   # or: an oidentd user config, kept up to date

In Docker, publish 113:1113 on the container that owns evrd's network and forward TCP 113 to the host. On a host where evrd runs natively, like the OpenBSD install, oidentd with ident_file works instead.

oidentd

With oidentd and nothing set up, networks get evrd's system user (_evrd) as the ident, which some refuse. Give evrd an ident file and it answers for each user with a bind host of their own (the network's ident or the username) and hides the rest, so networks use the ident from USER. It's rewritten within a minute of a bind host changing. Addresses more than one user binds, and the host's own default addresses, are left out. On OpenBSD:

shell · OpenBSD
mkdir -p /var/evrd/ident && chown _evrd /var/evrd/ident
usermod -d /var/evrd/ident _evrd         # oidentd reads ~_evrd/.oidentd.conf
echo 'ident_file /var/evrd/ident/.oidentd.conf' >> /etc/evrd/evrd.conf
cat >> /etc/oidentd.conf <<'CONF'
user _evrd {
	default {
		allow spoof
		allow spoof_all
		allow hide
	}
}
CONF
pkill -HUP -x oidentd; rcctl restart evrd

The file must be inside the chroot; oidentd reads it as root.

Metrics #

evrd exports OpenTelemetry metrics over OTLP/HTTP and reads them back from VictoriaMetrics for the dashboard's traffic chart and health numbers.

evrd.conf
otel_endpoint http://victoriametrics:8428/opentelemetry/v1/metrics
otel_interval 15s
metrics_url   http://victoriametrics:8428

Run VictoriaMetrics with -opentelemetry.usePrometheusNaming to get evrd_irc_lines_total, evrd_upstream_up, evrd_upstream_lag_seconds, evrd_irc_clients, evrd_cluster_users, evrd_history_queue and friends. Without metrics_url the dashboard still works, and the chart says metrics are off.

Behind a proxy with basic auth, put the credentials in both URLs (https://user:pass@vm.example.org). evrd sends them as basic auth, and Admin → Settings shows the password masked.

Traces

otel_traces_endpoint (or OTEL_EXPORTER_OTLP_TRACES_ENDPOINT) is an OTLP/HTTP traces URL, such as http://jaeger:4318/v1/traces. evrd sends spans for web API requests and the services behind them.

Grafana and Admin → Metrics

Admins see every metric under Admin → Metrics. For Grafana there's a ready-made dashboard in the evrd repository, deploy/grafana/evrd.json (a VictoriaMetrics or Prometheus data source with uid victoriametrics; change it on import): traffic, upstream links and lag, clients, sign-ins, users per node and the versions running.

Importing ZNC logs

evrctl history import-znc reads the files of ZNC's log module, per user (users/<user>/moddata/log/<network>/<buffer>/<date>.log) or per network, and loads them into the evrd user's networks of the same names, messages and channel events alike, so people moving from ZNC keep their old conversations. Point it at the ZNC user's directory (for example ~/.znc/users/admin), with -tz set to the time zone ZNC wrote its logs in (its user's Timezone setting; default UTC). -dry-run counts what would be imported and writes nothing. The imported networks keep everything from then on (backlog unlimited). With a Pebble store, stop evrd first, and run it once.
